# v2 Endgame 执行方案（已审阅并实施）

状态：用户于 2026-10-13 审阅并选择“按方案实现”。两种模式的离线期数、目标、已审核场地规则、触发状态、词条比较和场景文件已接入；实施细节及未决条款见 [v2 接入说明](v2-feature-notes.md)。本文件保留审阅时的计划，不作为新增游戏规则来源。

## 1. 目标与边界

首期实现 **危局强袭战** 和 **式舆防卫战**。用户选择模式、期数、难度/防线、试炼或房间、具体目标及场地增益，在现有单招式/异常/派生事件伤害计算中使用该场景，并同时计算新增一条副词条的收益。普通怪物模式继续可用，两种终局模式使用相同队伍、装备和计算内核。

遵循项目的静态场景约定：用户选择“当前 Buff 已触发”“当前层数”“Boss 当前阶段”等输入，不模拟战斗时间轴。时间评分、击杀评分、整场总分、轮换、资源循环、失衡积蓄耗时和通关预测不作为本次输出。临界推演与拟境湮灭战本期不接入，也不提供其空入口。

## 2. 已核对的数据与需要区别的结构

数据来源为 [式舆目录](https://zzz.nanoka.cc/shiyu/)、[危局目录](https://zzz.nanoka.cc/boss)和对应赛季详情，首版固定使用正式数据版本 `3.2`，不沿用 Nanoka 默认打开的测试版。保存原始响应、版本、源地址、读取时间与摘要散列；网站文案只作为规则审核证据，程序不通过任意文本匹配自动生成效果。

已验证式舆索引为 `https://static.nanoka.cc/zzz/3.2/shiyu.json`，中文赛季详情为 `https://static.nanoka.cc/zzz/3.2/zh/shiyu/{season_id}.json`。危局对应的索引和详情地址须按其页面实际引用核对并写入同步脚本，不靠遍历猜测 URL。

[式舆 62058](https://zzz.nanoka.cc/shiyu/62058)的正式期间为 2026-10-02 至 2026-10-16。其第五防线有多个房间，每个房间的增益与怪物组合不同，因此数据模型和界面不能固定为“两队上下半”。既保留防线、房间、波次，也允许用户指定本次攻击的单个目标。

[危局困难期数 690471](https://zzz.nanoka.cc/boss/690471)的正式期间为 2026-10-09 至 2026-10-23。页面区分 Boss 生命档位和实际战斗房间等级；例如生命档位 24 与战斗怪物等级 70 是两种字段，不能把生命档位当作敌人等级传给伤害公式。可选增益与 Boss 自带区域效果也是两种来源，分别保存。

国服时期按 Asia/Shanghai 展示开始/结束时间。源缺少时区说明时保留原文并注明国服约定，避免把前端本地日期当作正式期数身份。正式、未来、历史和测试期数按元数据标记；默认选择正在进行的正式期数，测试期数不混入正式选择。

## 3. 数据与规则分层

建议新增以下模块，依照现有角色、装备的“原始数据 → 人工审核映射 → 编译规则”结构实现：

| 层 | 建议位置 | 责任 |
| --- | --- | --- |
| 原始快照 | `core/data/endgame/{version}/{shiyu,boss}/` | 保存完整索引、详情、来源与摘要；历史期数不覆盖 |
| 归一化目录 | `core/data/endgame/loader.py` | 输出统一的期数、防线/试炼、房间、目标、候选增益关系 |
| 已审阅 Buff 映射 | `core/application/endgame/reviewed.py` | 每个 Buff 子条款的伤害类型、乘区、作用对象、条件、层数、快照规则及原文依据 |
| 场地编译 | `core/application/endgame/compiler.py` | 返回正式规则项、状态条件、参数与 diagnostics |
| 展示与请求翻译 | `core/presentation/endgame.py` | 校验期数归属，输出选择项，将命名输入变成正式场景 |
| 网页选择 | `frontend/src/components/EndgamePanel.tsx` | 模式、期数、目标、可选增益及当前状态选择 |

统一身份至少包含 `mode`、`season_id`、`stage_id`、`room_id`、`wave_id`、`target_id`、`monster_id/variant_id`、`buff_id`，不以怪物或 Buff 展示名关联。危局的难度、生命档位另存；式舆房间数量及每个房间目标数量由数据决定。

每个 Buff 子条款标记为 `implemented`、`out_of_scope` 或 `unresolved`。计分、回能、持续时间和失衡恢复速度等只影响战斗过程的条款，在本次静态单招式计算中标记为范围外，不伪造伤害倍率。未知伤害类型、作用范围、上限或互斥关系保留为未决项；只有与当前所选伤害有关的未知条款才产生局部不完整结果，不拖住无关角色、模式或期数的实现。

## 4. 敌人属性的来源优先级

普通目标使用已接入的真实怪物及其等级曲线。终局目标使用：**怪物基础变体 → 该期数/房间的明确覆写或倍率 → 用户显式手动覆写**。每个最终字段保留来源，尤其是防御、各伤害抗性、基础失衡倍率和 Boss 生命档位。

只将明确的字段或明确的乘法规则应用到目标，不能把房间顶部“弱点”汇总直接施加给所有怪物；也不能把异常积蓄抗性当作伤害抗性。同名 Boss 在普通图鉴与终局中可能是不同变体、阶段或特殊属性，关联时必须核对内部 ID。

若原始详情缺失关键字段，界面显示缺失并提供手动输入；恢复默认时只恢复该期数目标的源默认值。动态 Boss 阶段采用有来源的预设或明确状态选择，不根据名称猜测倍率。生命值只有在某条正式规则依赖当前 HP/最大 HP 时进入该规则的计算，不拿它去改变防御等级系数。

## 5. 场地 Buff 如何进入最终伤害

增加明确的场地来源类型与稳定来源 ID（如 `endgame:shiyu:62058:room:...:buff:...`），白盒明细展示模式、期数、房间和条款。场地规则仍使用现有 Effect/Modifier、Filter、Condition、Stack 与快照语义，不在 Calculator 外额外乘一个“场地总加成”。

需要审核新增“无角色 owner 的场地来源”匹配语义：仅在合法队伍/敌人目标范围内生效，职业、属性、招式和伤害类型 Filter 仍检查当前事件；不能把全队 Buff 当作某个队友的 self Buff。当前 `EffectSourceType` 没有独立场地类型，实施时应增加该来源类型及对应展示/序列化/匹配测试，避免冒充角色或音擎效果。

按子条款分别映射，示例以实际文字审核为准：

| 条款类型 | 计算接入 | 当前场景输入 |
| --- | --- | --- |
| 指定属性伤害加成 | 对应属性的普通增伤或面板通路，遵循项目分层 | 常驻，依属性匹配 |
| 攻击/生命/防御提升 | 正式 Panel Modifier，核对初始/当前快照与百分比基数 | 常驻或已触发状态 |
| 异常、紊乱、贯穿等特定伤害加成 | 对应伤害类型专属乘区，不能混成通用增伤 | 属性与类型 Filter |
| 防御降低、抗性降低 | 敌人对应 Modifier 路径 | 明确选择减益已生效 |
| 失衡易伤提升 | 现有失衡易伤结点，核对“加 N 个百分点”与“倍率乘 N%” | 实际失衡与对应状态 |
| 触发后若干秒内生效 | 当前状态/触发事实，不重放计时 | 用户选择当前已满足 |
| 叠层或互斥增益 | 命名层数参数、互斥组、服务端数量校验 | 合法层数及 Buff 选择 |
| 新伤害类型或未实装机制 | 有来源的局部 unresolved；先确认规则再扩展内核 | 不以已有类型代替 |

例如 62058 部分房间对冰/以太伤害以及异常后的减防有条款；690471 的候选增益含常驻面板加成和触发后的类型增伤。常驻部分和触发部分必须分别进入各自规则，不默认所有触发条件已经成立。其“锐化”等当前未纳入内核的条款须单独审阅，不能直接视作贯穿或普通增伤。

仍由 `CalculationScenario.enabled_rule_item_ids` 控制用户排除规则。场地固定规则默认选中；用户可关掉作对照，但不可打开不属于当前期数/房间的 Buff 或强行突破职业与属性条件。可选 Buff 的数量和互斥关系依据源规则，不写死“永远选一个”。

## 6. API、缓存与兼容

建议提供 `GET /api/v1/endgame/seasons?mode=shiyu|boss`、`GET /api/v1/endgame/seasons/{mode}/{season_id}`，响应仅来自已经审核并保存的快照。浏览器提交 `endgame_selection` 命名对象，包含合法期数、关卡、目标、候选 Buff 和状态参数；服务端验证这些 ID 的所属关系，再编译敌人和场地规则。浏览器不提交任意 Effect、Modifier 或场地乘数。

计算输出增加 `scenario_provenance`，包含数据版本、期数、关卡、目标、使用的 Buff、手动覆写及未决条款。旧计算请求没有 `endgame_selection` 时仍使用普通目标路径。新版场景保存采用独立、版本化的场景配置文件，不把敌人和期数偷偷放进现有单角色装备 v2 文件；旧角色配置保持可读取。

队伍的当前主控与固定槽位继续遵循已有约定。新增词条对比复用同一个已编译终局场景：每条只改 Build，不能重新选择 Buff、期数或目标，不能重复叠加场地规则。比较期间跨过规则阈值时重新求值适用条件，保持用户排除规则的意图。

使用随仓库打包的目录支持离线计算；更新期数通过显式同步、人工审核和测试后发布，打开页面或计算时不自动抓取并启用尚未审阅的新 Buff。缓存 ID 包含模式、数据版本和期数，历史快照不因“当前期数”更换而失去可重现性。

## 7. 具体执行顺序与交付

1. **数据快照与目录**：核对正式版两种模式的索引、详情、内部目标引用、房间和候选增益；保留一例多房间式舆、一例普通危局、一例困难危局及历史样例。交付源数据、归一化目录、缺失条款文档及离线 API。
2. **目标选择**：完成模式、期数、难度/防线、房间/试炼与目标选择，验证来源优先级、等级成长与期数覆写；切换期数后重置不再合法的 Buff 和状态输入。
3. **已明确场地规则**：从常驻面板/属性增伤和明确减防/失衡条款开始，逐个编译并自审。随后接入触发状态、层数和互斥关系；存在未决条款时记录并让其他可实现条款继续推进。
4. **完整计算与词条比较**：串联最终伤害、来源明细和三种展示模式，将场地场景传入所有新增词条对比；确认没有重复叠加。
5. **保存、迁移和页面验收**：增加场景文件导入导出与离线重现；通过历史期数、普通目标、不同主控、切换 Buff、手机宽度及未知条款的回归检查，整理说明与实现进度。

每一阶段保持可验证的小提交；提交和推送按用户明确授权执行，开发分支不自行合并。未决条款记录原文、来源、涉及乘区、已有证据和缺少的确认，不用名称猜测或数字近似堵住实现。

## 8. 验收清单

- 正式与测试期数分离，当前期数不依赖目录数组的第一项；历史期数可离线重现。
- 两种模式的房间、试炼、波次及目标从真实数据获得，支持多房间和多个 Boss，不硬编码二队或三个目标。
- 同一期数两个房间的不同 Buff 不串用；跨期数 Buff、非法层数与互斥选择在服务端被拒绝。
- 无 Buff 的结果与相同敌人/装备的普通场景一致；单个已知 Buff 的前后差值符合其正式乘区，且白盒来源只出现一次。
- 指定职业/属性/招式 Buff 只作用于合法事件；队友来源、异放/紊乱源快照、面板转化和直接/贯穿等伤害类型均有代表性回归。
- 危局生命档位不改变战斗等级；期数覆写与手动覆写的优先级可检查并可恢复。
- 新增一条词条与基准使用完全相同的终局场景，小词条收益和已满暴击收益处理正确。
- 未知的相关条款导致局部不完整并展示原因，无关未知条款不拖住其他结果；过程性计分/能量/计时条款不被编造成伤害。

## 9. 审阅时请确认的产品范围

建议采用：两种模式均支持正式历史期数与当前期数；测试期数先不进入产品；输出限定为用户当前招式/异常的静态伤害及词条收益；只通过当前状态选择表示触发与 Boss 阶段；评分与整场战斗模拟留在后续范围。用户审阅同意这些边界和以上接入方法后，开始 Endgame 实现。
